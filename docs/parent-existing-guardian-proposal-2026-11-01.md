# 在園児の保護者追加・招待で入力範囲を分ける案

2026-11-01 JST、モック版 `PARENT-EXISTING-GUARDIAN-MOCK-001`。ユーザーがモックに対し「両方に適用して実装」を選択し、画面と適用範囲を合意した。[本体の実装記録](parent-existing-guardian-implementation-2026-11-01.md)あり。同日、実機へ反映済み。[実機配備記録](deployment-parent-guardian-2026-11-01.md)あり。 [決定記録 SD-005](spec-decisions.md#sd-005)を参照。以下の調査・提案は合意前の検討過程を含む。

## 要望と確認した現状

ユーザーから、既存の児童への保護者追加で新入園と同じ入力画面になるとの報告があり、管理者の「在園児の保護者を追加・招待」と、招待先の「入園時の初回情報入力」の画像が提示された。画像の個人情報はモックへ転記せず、すべて架空データに置き換えた。

稼働コミット `c8990b8888c071a896ff58c2f81ada13fb1099e6` と、関連ソース7ファイルのハッシュを実機から読み取り、保存済み本番ソースとの一致を確認。業務DBは参照していない。

- `identity_page` は在園児の招待でも同じ `parent_auth/enrollment.html` を表示する。子どもの姓・名だけを初期入力し、カナ・生年月日・入園予定日・自宅住所も必須にする。在園児向けは19入力項目、必須13項目。
- `validate_enrollment_data(existing_child=True)` も園児の必須項目を要求する。既存園児での分岐は、主に2人目の保護者欄を使わないためのもの。
- `adding_guardian=True` の承認処理は園児・家庭共通項目を変更しない。そのため、この経路では更新に使わない園児情報も必須入力させている。
- 登録済みの保護者への初回入力依頼では園児・家庭共通情報も更新する。[既存仕様](guardian-account-sync.md)に園児情報を補ってもらう用途があるため、その用途と今回の「保護者アカウントの追加・招待」を分けて決める必要がある。

## こちらの解釈と画面案

今回の保護者アカウント登録では、在園児に同じ児童情報を入力し直してもらう必要はないと解釈した。管理者が選んだ園児との関係を確認し、本人の連絡先・勤務先を受け付ける画面に分ける案。

| 項目 | 修正案：在園児への追加・招待 | 新入園の個別招待 |
| --- | --- | --- |
| 見出し | 保護者アカウントの登録 | 入園時の初回情報入力 |
| 対象園児 | 招待にある氏名を表示。変更不可 | 現行の姓・名、カナ、生年月日、入園予定日を入力 |
| 保護者本人 | 姓・名・カナ2欄・続柄・電話は必須。勤務先・勤務先住所・勤務先電話は任意。9項目すべて維持 | 現行の本人9項目を維持 |
| 自宅住所・自宅電話・アレルギー・健康情報 | 今回の入力対象から除外。既存台帳を保持 | 現行どおり入力 |
| もう1人の保護者 | 追加欄なし。本人の申請だけ | 現行の任意入力を維持 |
| メールアドレス | 招待先を使用し、再入力しない | 同左 |

既存台帳にある保護者本人の個人情報を招待先へ事前表示する変更は含めない。モックの「入力済み」は架空の本人が入力した状態であり、台帳からの自動入力を示していない。

## 表示・保存・修正・取消

- 対象は、管理者の「この保護者を招待」「新しい保護者を追加」の両方。モック提示後に両方への適用を合意。同じ個別招待を使う園児詳細からの依頼と、旧形式申請の扱いは実装記録に明記した。
- 招待から入力画面へ進む既存の流れと、入力画面2時間・招待24時間の期限を維持する。
- 「入力内容を園に提出する」で申請を保存する。園の承認前は台帳・閲覧権限へ反映しない。
- 入力不足やエラーは入力済みの値を保持する。任意の勤務先3項目が空でも提出できる。登録済みの本人の任意情報を、空欄を理由に削除しない。
- 追加案の「入力をやめる」は確認を表示。取り消せば入力を保持し、終了すれば未提出の入力を保存しない。招待自体の取消・既存台帳の変更は行わない。
- 提出後の訂正は既存どおり園へ連絡する。本人に新たな提出済み編集機能は設けない。
- 園側の申請確認部分も、今回提出された本人9項目を表示する。確認理由・確認済みチェック・承認・却下を維持する。
- 承認で本人情報と選択済み園児の閲覧権限を反映し、パスワード設定案内を送る。別の保護者・きょうだいの閲覧権限、園児の氏名・日付・健康情報、家族共通の住所・電話は変更しない。

## 実装前にそろえる範囲

画面を隠すだけでは必須チェックで提出できない。画面、サーバー側の入力検証、承認時の更新対象、園側の提出内容表示、招待文言、マニュアルを同じ申請用途で分岐させる。

用途は招待時にサーバーで決め、保護者のPOSTやURL指定で園児・保護者の紐付け先や更新範囲を変えられないようにする。園児項目を不正に追加送信しても更新できないこと、本人以外・任意項目・兄弟の保持を回帰確認する。

既に発行済みの未提出招待、提出済みで承認待ちの旧形式申請、園児詳細からの「情報補完の依頼」との互換性は、実装時の確認事項。既存の提出内容を新仕様として黙って読み替えたり、旧申請の承認ができなくなったりしない扱いを決める。新入園と共通QRによる初回申請の情報収集は今回の省略対象にしない。
