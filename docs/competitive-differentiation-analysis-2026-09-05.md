# 既存の保育ICTとOPEN保育ICTの差別化分析

調査日: 2026-09-05<br>
OPEN保育ICTの確認対象: main `c759415`、カーネル構想は`kernel-lab/bootstrap`の仕様<br>
前提: ベータ実装前の開発方針を判断するための分析。完成した商用サービスとしての採点ではない。

## 結論

現在のOPEN保育ICTで最も明確な差別化は、園・法人側がソースコード、実行環境、業務データを扱い、自分たちで機能の変更と更新の判断をできることである。これはMITライセンスと自前で実行できる構成に根拠があり、将来のカーネル完成を待たずに存在する性質である。

一方、「保育業務を一元化」「帳票をカスタマイズ」「AIを活用」「オンプレで保存」「無償で利用」といった要素は、それぞれ既存サービスにも見られる。これらの単独の説明を独自性として押し出すと弱い。

将来のカーネルが加える価値は、園ごとの改修を積み重ねても共通部分の更新を受けられ、蓄積した記録と権限の意味を引き継げること。現在の「改修できる」という自由を、「改修したものを継続して育てられる」仕組みにすることである。これは現段階では設計上の仮説であり、実装済みの能力には数えない。

## 現状で言える差別化

### 1. 業務ソフトそのものの変更を選択できる

[リポジトリのMITライセンス](C:/python/open-hoikuict/LICENSE)は、条件に従った利用・改変・再配布を認める。技術担当者や支援者がいれば、項目や表示に加え、計算、権限判定、承認の扱い、連携処理をコードから変更できる。

調査した既存サービスの公開資料で確認できる帳票・設定の変更機能と、利用者側がアプリのソースを改修することは、変更範囲が異なる。各社の個別開発契約やソース提供条件までは確認していないため、「他社では絶対に不可能」とは主張しない。

園への実益は、標準機能で扱えない運用について、自分たちで対応する選択肢を持てること。ただし、コードを変える作業と、その後の動作確認・保守は必要であり、職員が画面からすべて自由に設定できる状態ではない。

### 2. データと実行環境を自分たちで管理できる

[自前起動の構成](C:/python/open-hoikuict/Dockerfile)、[ローカルDB](C:/python/open-hoikuict/database.py:14)、[施設文例DB](C:/python/open-hoikuict/plan_docs/runtime.py:9)、[バックアップ処理](C:/python/open-hoikuict/scripts/backup_runtime.py:440)がある。提供者が用意した画面上の出力に加え、自分たちでデータ抽出・変換処理を作ることができる。

これはデータを別製品へそのまま移せる保証ではない。データの意味・参照・添付・履歴を保持する変換は別途必要である。また、既存サービスのデータ所有権やエクスポート可否を否定する比較でもない。

オンプレ単独の独自性は弱いが、ソース・保存データ・実行環境を合わせて扱えることはOPENの特徴になる。

### 3. 改善の優先順位と採用する版を園側で選べる

Gitの履歴と実行用コードを保持できるため、改善の順序や採用する変更を自分たちで決められる。外部の支援者へ改修を依頼する余地もある。

現状のこれは技術者による開発・配備の自由である。ワンクリックで安全に更新できる機能、長期互換性の保証、AIが自動的に保守する仕組みが完成しているという意味ではない。依存ソフトの更新、脆弱性対応、DB移行は継続して必要になる。

### 4. 実装の検査と改良を共有できる

権限や記録の扱いをコードとテストで確認し、見つかった問題と修正を共有できる。これは透明性と共同改良の土台になる。オープンソースであることだけで、安全性や多数の開発者による保守が保証されるとは評価しない。

現在の[版付き設定](C:/python/open-hoikuict/child_records/models.py:14)や[保育計画の版管理](C:/python/open-hoikuict/plan_docs/store.py:306)は、その改良を積み上げる材料になる。承認・履歴機能そのものが競合より優れるという比較は、今回の資料だけではできない。

## カーネルで伸ばせる差別化

| 現在ある土台 | カーネルで目指す価値 | 今後必要な実証 |
| --- | --- | --- |
| コードを改修できる | 園ごとの差を設定・拡張として保持し、共通部分も更新できる | 項目・帳票・業務規則を一件変更し、共通部分の更新後も旧記録と変更が維持される |
| DBと記録を自分たちで扱える | 園・担当者・AIモデルが変わってもデータの意味を引き継げる | 安定ID、設定版、移行履歴、旧参照の互換対応 |
| ローカル認証と権限判定 | 画面・CLI・拡張・AIから同じ業務サービスと検証を利用する | 呼出元を変えても権限・競合・監査が同じ条件で機能する |
| AIによる開発支援を利用できるコード | AIが変更案を作り、検証・確認を経て適用できる | 変更の比較、検証対象の固定、適用、切戻しを一巡できる |
| 外部AIへの個人情報送信を制限する構想 | 園がAIの実行場所と利用範囲を制御できる | ローカルAI接続、分類、外部送信制御。現状の方針間の不整合も解消する |

この成長余地は、AIそのものが高性能になるだけでは実現しない。前回の[実装方針再考](C:/python/open-hoikuict/docs/beta-implementation-policy-review-2026-09-05.md)で挙げた、項目ID、競合検知、設定検証、更新の確定単位、移行履歴が、競争上の価値を支える実装になる。

## オンプレのメリットと引き受ける負担

| 園側が得る選択肢 | 同時に必要になること |
| --- | --- |
| 保存先、アクセス経路、バックアップ先を決められる | 機器・鍵・ネットワーク・復旧を管理する担当または支援者 |
| 独自の機能や連携を実装できる | 改修費用、試験、バージョン追従 |
| ソフトとデータを保持して継続利用を検討できる | OS・依存ソフト・機器の更新と保守 |
| 将来ローカルAIを組み込む構成を選べる | モデルの品質確認、計算資源、権限・送信制御 |

したがって、差別化の表現は「オンプレだから安全」「無償だから最安」「提供が止まっても永久に動く」ではなく、何を園側で管理・変更できるかを具体的にする。

現状の[画面共通部には外部CDN参照](C:/python/open-hoikuict/templates/base.html:7)があり、検討中のサーバー公開構成にはCloudflareも含まれる。完全な閉域動作や外部への通信ゼロを、現在の特徴としては掲げない。データのローカル保存とすべての通信が園内で完結することを区別する。

## 合いやすい利用者の仮説

- 園固有の運用を自分たちで改善したい園・法人で、技術担当者または継続支援する相手を確保できる。
- 保存環境やシステムの変更を自分たちで制御することに、運用負担を引き受けるだけの価値を感じる。
- 園と技術者が一緒に改善し、その成果を他の施設にも共有したい。

これらは今回の比較からの仮説であり、需要調査の結果ではない。最初から一般の園すべてが自前運用を望むと仮定しない。園職員全員が開発者になる前提も置かない。

運用や問い合わせをサービス提供者に任せることを重視する園には、既存の提供形態が合う場合がある。OPEN側はソフトの自由と継続支援を両立する提供方法も検討できるが、その支援体制は現状の提供済みサービスには数えない。

## ベータ段階の説明として勧める表現

> OPEN保育ICTは、園の業務データと仕組みを自分たちの環境で扱い、必要な機能を自分たちの判断で育てられる、オープンソースの保育ICTです。

将来像を添える場合は、園ごとの変更と共通部分の更新を両立するカーネルを開発する構想であることを明示する。「AIが園に合わせて安全に自動改修できる」と現在形では説明しない。
