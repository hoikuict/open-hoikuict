# カーネル仕様と現行mainの整合性確認

確認日: 2026-09-05

カーネルとして成長させる方向性は現行アプリと整合している。ただし、カーネル仕様が記述する現状と、その後に実装された認証・権限・記録・通知・保存構成には差がある。現行機能を引き継ぐ対応表と移行時の受入条件を補ってから実装に使う必要がある。

これは確認結果と修正提案であり、カーネル仕様の改訂やコードの変更、ブランチの統合は行っていない。

## 実装前に仕様へ反映する事項

ここでの「要更新」は、現在のアプリで障害が発生しているという意味ではない。カーネル仕様に沿った移行によって、現在の意味や保証を失わないための条件である。

### 1. 「現状は1つのDB」という記述が実装と一致しない

カーネル仕様3.2・3.3節（119・143行）と22節（1171行）は1つのDBを前提とする。一方、現在は主業務DBに加え、書き込み可能な施設文例DBと添付ファイルがある。

- [施設文例DBの配置](C:/python/open-hoikuict/plan_docs/runtime.py:9)
- [施設文例の独立した接続・commit](C:/python/open-hoikuict/plan_docs/services/bunrei.py:314)
- [2つのDBと添付ファイルを取得するバックアップ](C:/python/open-hoikuict/scripts/backup_runtime.py:440)

**修正案:** 「現行は複数の保存先を持つ」と明記し、1DBは目標構成として分ける。施設文例を主DBへ移すか、別ストアとして残すかを決定する。後者なら共通トランザクションが及ぶ範囲、障害時の整合性、バックアップ・復元単位を定義する。添付ファイルも復元単位から外さない。

### 2. 認証・保護者との関係・職員権限の引き継ぎが具体化されていない

カーネル仕様6・7節の主体・関係・権限という考え方は一致するが、現行エンティティからの対応表が不足している。

- 職員はUUIDを持つ`User`で、3段階ロールに加え、児童記録管理・請求口座管理などの権限を持つ。[モデル](C:/python/open-hoikuict/models.py:2466)
- `Guardian`とログイン主体の`ParentAccount`は別のモデル。園児へのアクセスは`ParentChildLink`による明示的な関係を維持する必要がある。[保護者アカウント・関係](C:/python/open-hoikuict/models.py:1098)
- `family_id`は家族のグループ化用で、認可の根拠にはしない。家族をまとめてもアクセス対象の園児を自動追加しない。[既存の明示的な方針](C:/python/open-hoikuict/family_support.py:287)
- 保護者の認証停止ではセッションや復旧用状態などを失効させる。[停止処理](C:/python/open-hoikuict/parent_auth.py:1360)

**修正案:** `User → staff actor`、`ParentAccount → parent actor`、`Guardian → 関係者情報`、`ParentChildLink → アクセス関係`を定義する。ロール名の置換だけでなく追加権限、所属期間、停止・復旧・招待承認の挙動を移行契約にする。家族のグループ化から権限を推測しないことをCoreの不変条件に加える。

### 3. 「担当クラス内」という認可の例を全操作に適用すると現行の挙動が変わる

カーネル仕様7.2節の判定例（318行）は担当クラス内か管理権限ありを条件にする。現行の経過記録は、既定では全職員が閲覧でき、作成には担当等の権限が必要である。観察記録の閲覧は別の判定を使う。[閲覧・作成の判定](C:/python/open-hoikuict/child_records/access.py:19)

さらに、保育計画の認証アダプターは現在、園内のクラス名一覧を`classroom_refs`に設定する。これは職員ごとの担当クラスID一覧と同じ意味ではない。[アダプター](C:/python/open-hoikuict/plan_docs/auth_adapter.py:83)

**修正案:** 「経過記録閲覧」「観察記録閲覧」「作成・編集」「承認」「請求口座管理」を別の操作として定義する。既存設定の引き継ぎ表を作り、カーネル仕様の認可例は操作ごとの条件であることを明記する。

### 4. 安定IDへ移行する方針は一致するが、名前由来の参照を残す対応が必要

カーネル仕様6.2節はUUIDと既存整数IDの互換エイリアスを認めている。この方針は現在の連携契約と矛盾しない。ただし、現在の`nursery_ref`は環境設定値、`classroom_ref`はクラス名を使う。個別計画の`child_ref`は`child:{children.id}`形式である。[現行契約](C:/python/open-hoikuict/docs/integration-contract.md:18)、[園児参照](C:/python/open-hoikuict/docs/integration-contract.md:134)

**修正案:** 公開IDと旧参照値の対応表を導入し、既存の文書・文例・根拠参照を解決できるようにする。園名やクラス名を変えた際の旧文書参照も受入試験に含める。`actor_ref`、文書種別・状態、セクションキー、根拠参照の互換性を維持する。

### 5. UTCへの統一には、項目ごとの時刻移行規則が必要

カーネル仕様9.2節（390行）は永続化する瞬間をタイムゾーン付きUTCとする。現行の登降園はローカルのタイムゾーン情報なし日時、同じ処理の更新監査はUTCという使い分けがある。[打刻処理](C:/python/open-hoikuict/routers/attendance.py:824)

また、SQLiteから読み戻したUTC監査日時もタイムゾーン情報なしになることを前提に、表示時にUTCとして扱っている。[時刻ヘルパー](C:/python/open-hoikuict/time_utils.py:50)

**修正案:** 各項目を「UTCの瞬間」「施設の現地時刻」「業務日付」に分類する。既存のタイムゾーン情報なし値を一律にUTCと解釈しない。登降園・日跨ぎ・延長料金の計算結果が移行前後で一致する試験を追加する。日本時間をUTCと誤認した場合は9時間ずれるため、移行前に固定するべき契約である。

### 6. 外部AIへの送信方針は、既存の日案仕様との優先関係を明確にする

カーネル仕様16.1節（737〜739行）は、実在の個人・健康情報を外部AIへ送ることについて、施設設定や管理者承認による例外を認めない。一方、現行の日案仕様には「外部送信禁止を既定、例外は施設設定と明示同意」とあり、AI支援の節でも条件付きの外部API利用を認める。[日案仕様の比較表](C:/python/open-hoikuict/docs/spec-daily-plan-v1.md:47)、[AI支援の規則](C:/python/open-hoikuict/docs/spec-daily-plan-v1.md:498)

**修正案:** カーネル準拠の機能では外部AIへ送れる情報の範囲をカーネル仕様で固定し、日案側の同意・設定による許可はその範囲内だけに適用する。実在情報を加工・要約・マスクしたものを自動的に送信可能とみなさない。自由記述や施設文例も、名称だけで安全な情報に分類しない。

これは文書上の不整合であり、この確認で外部AIへの実データ送信を発見したという意味ではない。現行の保育計画コードに、仕様が描く共通AI Gatewayや分類強制の実装は確認できず、将来機能として評価する。

### 7. 既存の通知処理・記録機能を、移行元として仕様に追加する

カーネル仕様11節・Phase 1は共通Outboxの導入を計画する。現在は保護者通知・端末別配信・認証メールに、保存された配信状態や再試行の仕組みがある。[通知と端末別配信](C:/python/open-hoikuict/models.py:1903)、[配信処理](C:/python/open-hoikuict/parent_push_service.py:465)、[認証メール](C:/python/open-hoikuict/models.py:1220)

**修正案:** 既存キューをそのまま汎用Outboxと見なさず、共通イベントから既存の配信処理へ接続する契約を作る。重複防止キー、再試行、処理中リース、`accepted`・`shown`・`clicked`の意味を維持し、旧処理と新処理の二重送信を防ぐ。

モジュール一覧には、現在の[児童記録](C:/python/open-hoikuict/child_records/models.py:1)、[園内記録・系列・ハイライト](C:/python/open-hoikuict/models.py:2194)、バックアップ運用の責務も追記する。保育計画にはすでに版管理と楽観ロックがあるため、共通化の際はその保証を引き継ぐ。[保存処理](C:/python/open-hoikuict/plan_docs/store.py:306)

## 整合している点と未実装の区別

| 観点 | 確認結果 |
| --- | --- |
| 段階的なカーネル化 | FastAPI・SQLModelを使った現行構成を保ち、境界を順に作る方針は適合する。全面的な作り直しを要求しない仕様になっている。 |
| 認証・関係・権限を中心に据える | 現行のローカル認証、明示的な保護者紐付け、職員権限はカーネルへ引き継げる基盤である。 |
| 承認・監査・版の保護 | 日案の承認版保護・変更履歴・競合検知など、目標に沿う実装が存在する。全機能で共通化済みとは評価しない。 |
| 安定した契約と互換性 | 現行の保育計画契約と、仕様の公開ID・互換エイリアス方針は一致する。具体的な移行表は必要。 |
| カーネル独自の実装 | このブランチの独自差分には存在しない。実装されたカーネルの性能・安全性・完成度を測る段階ではない。 |
| 汎用拡張SDK・マニフェスト・AI Gateway・変更セット適用・複数施設分離 | 仕様上の目標。現在のコードや今回のテスト合格だけでは、これらを実装済み・保証済みと評価できない。 |

仕様26節では、施設モデルの移行、正式なマイグレーション基盤、拡張保存方式などを既に未決事項として挙げている。未決であること自体を新たな欠陥とは扱わない。今回必要なのは、その検討に現行実装の具体的な契約を加えることである。

## 実機検証とカーネル開発の進め方

1. 現行mainを実機検証の基準として固定し、2つのDB・添付・認証状態を含む復元、端末からの操作、通知と再起動後の挙動を確認する。
2. カーネル仕様の別改訂版で、上記の保存構成・主体と権限・参照ID・時刻・AI方針・既存キューの移行表を補う。
3. カーネル開発の基準を現行mainまで進め、既存テストを維持しながら、認証コンテキスト・権限・時刻・監査の境界を小さく抽出する。
4. 最初の共通化では一つの業務経路に絞り、通常操作に加え、権限拒否、版競合、再起動、重複イベント、旧データ読込を検証する。
5. その基盤を確認してから宣言型カスタマイズやAIを接続する。AIの能力向上を取り込む際も、既存のデータ・権限・記録の意味を維持できることを受入条件にする。
