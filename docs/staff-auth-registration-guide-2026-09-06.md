# 職員認証・登録手順書

作成日：2026-09-06<br>
対象：OPEN保育ICT、職員のローカルパスワード認証<br>
確認した実装：`c759415960d4eae04401cd28c2e3f967868279e4`

既存資料とは別に作成した、現在の実装に基づく手順書です。管理者が職員を登録して有効化コードを発行し、職員本人がログインIDとパスワードを設定します。**職員名簿への追加だけではログインできません。**

保護者の登録は[保護者認証・登録手順書](parent-auth-registration-guide-2026-09-06.md)を参照してください。

## 1. どこから始めるか

| 現在の状態 | 開始する手順 |
|---|---|
| ログインできる管理者がいる | 第3章「管理者が職員を追加する」 |
| 初期管理者もまだ作成していない | 第7章「最初の管理者を作る」 |
| 職員・管理者は名簿にいるが、パスワードを設定していない | 管理者がログインできれば第3章の認証管理から。誰もログインできなければ第8章の既存職員有効化CLI |
| 設定済みのパスワードを忘れた | 第6章「パスワードを再設定する」 |

## 2. 登録前に確認すること

施設の利用URLを決め、以下のパスをそのURLの後ろに付けてアクセスします。例のドメインを実際の施設URLへ置き換えてください。

| 用途 | パス |
|---|---|
| 職員ログイン | `/staff/login` |
| 職員管理 | `/staff/users` |
| 有効化・初回パスワード設定 | `/staff/activate` |
| パスワード再設定 | `/staff/reset-password` |
| 職員権限設定 | `/staff/permissions` |

例：施設URLが `https://hoiku.example.jp` なら、有効化画面は `https://hoiku.example.jp/staff/activate` です。

サーバー担当者は、利用中のアプリが次の設定で起動していることを確認します。

```dotenv
HOIKUICT_ENABLE_MOCK_AUTH=0
HOIKUICT_STAFF_AUTH_MODE=local_password
```

これは認証方式の確認項目です。サーバー起動に必要な設定一式は[サーバー稼働仕様書v2](pilot-deployment-spec-v2.md)、Windowsでの認証版βは[環境別運用ルール](environment-profiles.md)を参照してください。

職員を選択するだけのログイン画面はモック認証です。その画面での利用確認を、パスワード認証の登録完了として扱わないでください。

## 3. 管理者が職員を追加する

### 3.1 職員情報を登録する

1. 管理者本人のアカウントで `/staff/login` からログインします。
2. 「職員管理」(`/staff/users`) を開き、「職員を追加」を押します。
3. 以下を入力します。

| 項目 | 入力・確認内容 |
|---|---|
| 表示名 | 対象職員の氏名 |
| メールアドレス | 他の職員と重複しない連絡先。ここに入力しても有効化メールは自動送信されません |
| 権限 | 「管理者」「編集可」「閲覧のみ」から担当業務に合わせて選択 |
| 表示順 | 通常は初期値の `100`。現実装では `200` 以上が職員認証対象から除外されるため、登録する職員は `200` 未満にする |
| 有効 | チェックを入れる |

4. 「職員を追加」を押します。
5. 作成した職員の「認証管理」へ移動したこと、対象氏名が正しいことを確認します。

既に名簿にいる職員は追加し直さず、職員管理の対象行から「認証管理」を開きます。

### 3.2 有効化コードを発行する

1. 対象職員の「認証管理」でログインIDを入力・確認します。初回の候補は職員のメールアドレスです。
2. 「発行理由」に、たとえば「新規採用職員の初期設定」と入力します。
3. 「有効化コードを発行」を押します。
4. 表示された対象職員、6文字の有効化コード、有効期限、案内先を確認します。
5. 本人確認のうえ、施設で決めた個別の連絡方法で以下を本人へ渡します。

   - 施設の有効化画面URL：`施設URL/staff/activate`
   - 有効化コード
   - 発行時のログインIDと、有効期限

**コードは発行から30分、1回限り有効です。表示画面を閉じた後に同じコードを再表示する機能はありません。** 紛失・期限切れの場合は認証管理から再発行します。コードやパスワードを共用の作業記録へ残さない運用にしてください。

この段階の認証状態は「有効化待ち」です。管理者が職員のパスワードを指定する操作はありません。

## 4. 職員本人が初回設定する

1. 管理者から受け取った有効化画面URLを開きます。
2. 「有効化コード」に6文字のコードを入力し、「コードを確認して次へ」を押します。
3. 「ログイン情報を設定」画面の対象氏名とログインIDを確認します。ログインIDはこの画面で変更できます。施設でIDの命名ルールがある場合はそれに合わせ、確定したIDを控えます。
4. 「新しいパスワード」と確認欄に、本人が決めた同じパスワードを入力します。
5. 「ログイン情報を設定」を押します。
6. 職員ログイン画面へ戻ったら、確定したログインIDとパスワードでログインします。

パスワードは8〜128文字です。氏名・ログインID・メールアドレスを含むものや、拒否リストにある推測しやすいものは受け付けられません。拒否された場合は画面の理由に従って別のパスワードを設定してください。

**有効化が完了しても自動ログインはされません。** また、職員の連絡先メールアドレスとログインIDは別の項目です。本人が初回設定で変更した場合は、変更後のIDでログインします。

## 5. 管理者が権限・担当クラスを確認する

1. 職員管理で「設定済み」、対象職員の認証管理で「認証設定済み」と表示されることを確認します。
2. 職員管理の「権限設定」(`/staff/permissions`) で、基本権限と「園児台帳管理」「請求管理」などの業務別権限を確認・保存します。職員追加時に業務別権限が一式付くわけではありません。
3. 担当クラスが必要な職員は、職員管理の対象行から「担当クラス」を開きます。
4. クラス、担当区分、開始日、必要なら終了日・主表示を設定し、「追加する」を押します。開始日・終了日が実際の担当期間と合っていることを確認します。
5. 職員本人のアカウントで、担当業務に必要な画面が開けることを確認します。

登録完了の確認欄：

- [ ] 職員本人が自分のログインID・パスワードでログインできる。
- [ ] 認証状態が「設定済み」、職員情報が「有効」になっている。
- [ ] 基本権限と業務別権限が担当業務に合っている。
- [ ] 必要な担当クラスと担当期間が設定されている。
- [ ] ログアウト後、再びログインできる。

## 6. パスワードを再設定する

1. 管理者が本人確認を行い、対象職員の「認証管理」を開きます。
2. 理由を入力し、「再設定コードを発行」を押します。
3. 本人へ6文字のコードと `施設URL/staff/reset-password` を渡します。
4. 本人が再設定コード、新しいパスワード、確認用パスワードを入力し、「パスワードを再設定」を押します。
5. 新しいパスワードでログインします。

再設定コードも30分・1回限りです。有効化コードと再設定コードは用途が異なります。初回登録は `/staff/activate`、設定済みパスワードの再設定は `/staff/reset-password` を使用します。

## 7. 最初の管理者を作る［サーバー担当者］

有効な管理者がまだ存在しないDBに対して、`bootstrap-admin` を一度実行します。**有効な管理者の名簿が既にあれば、その管理者がパスワード未設定でも新規作成は拒否されます。** その場合は第8章を使用します。

### 7.1 Windows認証版βの場合

準備済みの `.env.beta.local` を使い、アプリと同じリポジトリ・DBへ登録します。CLI単体は `.env` や `.env.beta.local` を自動で読みません。次の補助コードは、設定ファイルを確認して読み込んでからCLIを起動します。

```powershell
Set-Location -LiteralPath C:\python\open-hoikuict
$authSetup = @'
import os
import sys
from pathlib import Path
from dotenv import dotenv_values, load_dotenv

env_file = Path('.env.beta.local')
if not env_file.is_file():
    raise SystemExit('.env.beta.local がありません。環境を準備してください。')
config = dotenv_values(env_file)
if not config.get('HOIKUICT_DATABASE_URL'):
    raise SystemExit('設定ファイルに登録先DBを明示してください。')
if config.get('HOIKUICT_STAFF_AUTH_MODE') != 'local_password':
    raise SystemExit('職員認証を local_password に設定してください。')
for key in ('HOIKUICT_DATABASE_URL', 'HOIKUICT_STAFF_AUTH_MODE'):
    if key in os.environ and os.environ[key] != config[key]:
        raise SystemExit(key + ' がシェルと設定ファイルで異なります。起動中アプリの設定と照合してください。')
load_dotenv(env_file, override=False)

import database
url = database.engine.url
if url.get_backend_name() == 'sqlite' and url.database:
    print('登録先DB:', Path(url.database).resolve())
else:
    print('登録先DB:', url.render_as_string(hide_password=True))
from scripts.auth_user import main
raise SystemExit(main([sys.argv[1]]))
'@
.\venv\Scripts\python.exe -c $authSetup bootstrap-admin
```

表示された登録先DBが、起動中アプリのDBと一致することを確認してから、CLIの入力を進めます。標準のβ設定では `C:\python\open-hoikuict\hoikuict-beta-auth.db` です。異なるDBが表示された場合は中止して設定を確認します。

### 7.2 Dockerで稼働するサーバーの場合

利用中のCompose構成のディレクトリで、起動済みの `app` コンテナ内から実行します。実行対象のサービス名が異なる構成では、そのサービス名を使います。

```sh
docker compose exec app python -m scripts.auth_user bootstrap-admin
```

Composeの環境変数とDBの保存先が準備済みであることが前提です。配布Composeを無設定で起動するための手順ではありません。構成は[サーバー稼働仕様書v2](pilot-deployment-spec-v2.md)を参照してください。

### 7.3 CLIで入力する内容と完了確認

順に「表示名」「連絡先メールアドレス」「ログインID」「作成理由」「実行者」「承認者」を入力します。内容が正しければ、CLIの「この内容で作成しますか [yes/N]」へ `yes` と入力します。

作成後に表示される6文字の有効化コードを使い、第4章と同じ方法で管理者本人がパスワードを設定します。ログイン後に職員管理を開ければ、初期管理者の登録は完了です。

通常の起動スクリプトは、初期管理者やサンプル職員を自動作成しません。認証のためにDBを削除したり、デモデータの投入を行ったりする必要はありません。

## 8. 既存職員の初回有効化CLI［サーバー担当者］

名簿はあるが本人がまだ認証設定していない場合や、初期管理者のコードが期限切れになった場合に使用します。

Windows認証版βでは、第7章の `$authSetup` を同じPowerShellで定義したうえで、末尾の実行を次に変更します。

```powershell
.\venv\Scripts\python.exe -c $authSetup activate-staff
```

Dockerの場合：

```sh
docker compose exec app python -m scripts.auth_user activate-staff
```

1. 一覧の氏名・メールアドレス・認証状態を確認し、対象職員の番号を入力します。
2. ログインID、発行理由、実行者、承認者を入力します。資格情報が既にある場合は、登録済みのログインIDを使用します。
3. CLIの確認へ `yes` と入力し、コードを受け取ります。
4. 本人が第4章の有効化手順を実施します。

一覧の対象は「有効」かつ表示順が `200` 未満の職員です。「認証設定済み」で停止されていない職員は、このCLIでは再発行できません。パスワードを忘れた場合は第6章を使用します。

## 9. うまく進まない場合

| 症状 | 確認・対処 |
|---|---|
| 職員を選ぶだけのログイン画面が出る／認証画面を利用できない | 起動中アプリの認証モードを確認。`mock`・`disabled` では本書の登録にならない |
| 職員を追加したがログインできない | 「認証管理」でコードを発行し、本人のパスワード設定まで完了したか確認 |
| 有効化コードが使えない | 30分以内か、最新のコードか、使用済みでないか、職員用画面かを確認。必要なら再発行 |
| 職員が認証対象に出ない／有効なのにログインできない | 職員情報の有効チェックと表示順 `200` 未満を確認。認証停止からの再開には有効化手続きも必要 |
| ログインIDが重複している | 別のIDを設定。連絡先メールとログインIDを混同しない |
| ログインできるが業務画面を操作できない | 職員権限設定、担当クラス、担当期間を確認 |
| 入力を繰り返した後にログインできない | 一時的な試行制限の可能性があるため連続試行を止め、時間を置く。必要なら管理者へ連絡 |
| 「CSRFトークンが不正です」 | 正しい施設URLから画面を開き直し、Cookieを許可。同じ手続き中にホスト名を切り替えない |
| 初期管理者を作れない | 有効な管理者が既にある場合は `activate-staff` または既存管理者による操作。新規作成で回避しない |
| 全管理者が設定済みパスワードを失い、誰もログインできない | 現行CLIには設定済みパスワードの汎用リセット手順がない。保守担当者へ引き継ぐ。DB削除・再初期化で復旧しない |

## 10. 今回確認した範囲

実装・テンプレートと、職員17件・保護者9件の既存認証テストを確認し、計26件が成功しました。さらに実際の `main.app` と隔離した合成データのDBで、初期管理者の作成、有効化、ログイン、画面からの職員追加、コード発行、本人の初回設定、ログインまでのHTTP処理を確認しました。CSRF保護を有効にして実施しています。

第7章に掲載した補助コード自体も隔離環境で実行し、指定した設定ファイルのDBに初期管理者が作成されること、シェルのDB設定が異なる場合はDB作成前に停止することを確認しました。

本書のために実際の職員アカウントを追加したり、既存DBを書き換えたりはしていません。実機ブラウザの表示・操作や、本番サーバーの環境設定は今回の検証に含みません。
