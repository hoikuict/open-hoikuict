# カレンダー権限・繰り返し予定・延長保育料金転送の検証

検証日: 2026-09-28  
対象: 現在の作業ツリー（HEAD `ab947ba718a8d2c64da66e2cafb255f01cda14ad`）。配備環境での検証ではない。

3点とも再現した。アプリケーション本体は変更せず、架空データを使う診断スクリプトと結果を追加した。

## 1. 閲覧のみへの変更後も既存予定を操作できる — 再現

実際の `local_password` 認証で管理者・編集職員をログインさせ、予定を作成した。その後、管理者から `POST /staff/permissions/{user_id}` で職員を `view_only` に変更した。職員は新しいTestClient（Cookieを引き継がない）でパスワードを再入力してログインし、認証結果が `view_only` であることを確認した。

`GET /calendar` による権限同期後も、個人カレンダーのメンバー権限は `owner`、共有カレンダーでは `editor` のままだった。

| 予定の条件 | 移動 | 終了時刻変更 | 削除 | 通常の編集保存 | 新規作成 |
| --- | --- | --- | --- | --- | --- |
| 自分の個人カレンダー・自分の予定 | 200・保存された | 200・保存された | 303・削除された | 403・拒否 | 403・拒否 |
| 共有カレンダー・自分の予定 | 200・保存された | 200・保存された | 303・削除された | 403・拒否 | 403・拒否 |
| 共有カレンダー・他職員の通常公開予定 | 200・保存された | 200・保存された | 303・削除された | 403・拒否 | 403・拒否 |

HTTP応答だけでなく、別のDBセッションで開始日時・終了日時・削除フラグの更新を確認した。通常の編集保存が拒否された予定のタイトルは変化していない。

原因は、既存メンバーを更新しない同期処理と、最新職員権限を考慮しない編集・削除判定の組み合わせ。

- `routers/calendar.py:282` — `_sync_staff_shared_calendars` は既存メンバーをスキップ。
- `calendar_service.py:562` — `_permission_flags` はメンバー権限と作成者で判定し、`context.user_can_edit` を確認しない。
- `routers/calendar.py:2002` / `2062` / `1873` — 移動・終了時刻変更・削除は、この判定に従う。
- `calendar_service.py:61` と `routers/calendar.py:1660` 付近 — 新規作成・通常の編集保存は最新職員権限を含む `can_create_events` を確認するため拒否される。

修正方針の提案: 最新職員権限を予定操作の共通判定に反映する。共有メンバーの同期だけでは、個人カレンダーの所有者や予定作成者による操作を防げないため、それだけで修正完了とはしない。

## 2. 繰り返し予定の1回だけの移動が表示期間から欠落する — 再現

毎週月曜日、2026-09-14開始、全3回、09:00〜10:00 JSTの予定を作成。そのうち9月21日の1回だけを移動した。移動APIと「この回だけ」の編集保存の両方で確認し、同じ結果になった。個別変更の移動先日時はDBに正しく保存されている。

以下の件数は、シリーズ全体ではなく、元日時が9月21日の対象回だけを数えたもの。実際に返されたHTMLの予定詳細リンクから数えた。

| 移動先 | 移動先の日表示 | 移動先の週表示 | 移動先の月表示 | 移動先の日付だけで検索 |
| --- | ---: | ---: | ---: | ---: |
| 9月22日（同じ週） | 0 | 1 | 1 | 0 |
| 9月29日（別の週） | 0 | 0 | 1 | 0 |
| 11月3日（別の月） | 0 | 0 | 0 | 0 |

本来は、いずれの移動先表示・検索でも対象回が1件出るべき。元の日付も表示期間内に含まれる週・月表示では表示されるため、表示モードによって見え方が変わる。

移動元の9月21日の日表示には残らず、0件だった。一方、**9月21日だけを条件に検索すると移動後の予定が1件残った**。元と先の両方を含む広い検索期間では1件で、今回の条件では重複はなかった。

原因:

- `calendar_service.py:393` 付近 — 元日時が表示期間に重なる候補だけを生成。
- `calendar_service.py:513` 付近 — 候補生成の後で個別変更の日時を適用。
- 個別変更後の期間判定もないため、移動先では抽出漏れ、移動元の検索では期間外の混入が起きる。
- カレンダーの描画は `routers/calendar.py:459` の日別振り分けで再度重なりを確認するため、移動元の日表示には残らない。

修正方針の提案: 移動先が対象期間に重なる個別変更も取得し、変更後の実日時で期間判定する。元候補との重複を防ぎ、取消済みの回も除外する。

## 3. 同月の同時転送で片方がHTTP 500になる — 競合条件下で再現

ファイル形式の一時SQLite DBを使用。WAL、`foreign_keys=ON`、`synchronous=NORMAL`、`busy_timeout=15000` を設定した。異なる2職員に対応するHTTPクライアントから同月を転送し、各リクエストは独立したSQLModel Session・DB接続を使用した。

架空の1家族・1園児・確定済み2日分（100円と250円、計350円）を使用した。

競合を確実に作るケースでは、SQLAlchemyの実行直前フックを使い、両接続が対象行を未登録と判断してからINSERTする直前で待ち合わせた。サービス関数、SQL、DB例外、HTTP応答は差し替えていない。INSERT時の接続識別子が異なることも確認した。

| 初期条件・待ち合わせ箇所 | 回数 | HTTP応答 | 捕捉したDB例外 |
| --- | ---: | --- | --- |
| 費目も未登録、費目INSERT直前 | 3 | 片方303、片方500 | `UNIQUE constraint failed: fee_items.code` |
| 費目登録済み・請求未登録、請求INSERT直前 | 3 | 片方303、片方500 | `UNIQUE constraint failed: billing_claims.billing_cycle_id, billing_claims.family_id` |
| 費目・請求登録済み・明細未登録、明細INSERT直前 | 3 | 片方303、片方500 | `UNIQUE constraint failed: billing_charge_lines.source_reference` |
| リクエスト開始だけを同時化し、途中の待ち合わせなし | 3 | 両方303 | なし |

したがって、同時操作のたびに必ず500になるという結果ではない。両方が未登録と判断する競合順序で発生することを確認した。

全12回について、処理完了後のDBで次を確認した。

- 請求1件、延長保育の請求明細1件、転送ログ1件。
- 請求合計・明細金額とも350円。明細はロック済み。
- 元の料金2件は同じ明細に紐付き、転送額は100円と250円。
- `PRAGMA foreign_key_check` の違反0件。
- 失敗した職員が新しいリクエストで再試行すると303となり、「変更はありませんでした」と応答。件数・金額・紐付けは増減しなかった。500が出なかったケースでも同じ再試行結果。

今回の条件では二重請求や金額の不整合は再現せず、一意制約により重複は防がれた。応答処理の不備は再現した。

原因:

- `extended_care_billing_transfer_service.py:639` / `655` / `430` 付近 — 費目・請求・明細を検索してから作成するため、未登録判定が競合し得る。
- `routers/extended_care_fees.py:170` — `ExtendedCareBillingTransferError` だけを捕捉し、`IntegrityError` を業務上の応答や再試行に変換していない。

修正方針の提案: 同月の転送を直列化するか、競合時にロールバックして新しい状態から転送全体を再判定する。一般のDBエラーを一律に成功扱いせず、一意制約競合とその他の失敗を区別する。
