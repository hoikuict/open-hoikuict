# ドキュメントの更新

この本番用ブランチでは、実機へ反映した機能のマニュアル・合意・配備記録をコードと一緒に管理します。`python -m mkdocs build --strict` とリンクを確認してからコミットします。mainとの統合や公開サイトの配備は別の操作です。

## 仕様の合意・変更・疑義を残す {#decision-records}

2026-11-01 JSTから、[仕様の決定・変更記録](spec-decisions.md)を共通の参照先とします。機能ごとの仕様書はそのまま維持し、決定記録と相互に参照できるようにします。

1. **対象を分ける**：対象機能・操作・権限・文書状態を明記し、要望、こちらの解釈、未確定事項を区別します。たとえば「管理者が編集できる」と「管理者名を担任欄へ自動入力する」は別の決定です。
2. **合意の根拠を残す**：合意日、確認できる会話・文書・モックの版を記録します。会話の識別子やリンクが取得できない場合はその旨と、日付・対象・必要最小限の発言を残し、参照を捏造しません。
3. **変更前の記録を残す**：新しい決定に旧IDと置換範囲を記載し、旧文書の冒頭にも新しい記録への参照を置きます。一部変更を文書全体の廃止と扱いません。最終合意に疑義があれば、旧決定を消さず「最終合意要確認」として追記します。
4. **合意・実装・配備・検証を分ける**：作業場所、ブランチ、コミット、未コミット差分の有無、配備先の版、確認日時・方法・結果を記録します。未コミット差分を含む場合は、可能なら差分や対象ファイルのハッシュを保存し、保存できていなければ再現性の限界を明記します。
5. **確認できていない点を引き継ぐ**：既存タスクの完了やコードの存在を、問題解決・最新の合意・本番反映の証拠に置き換えません。古い検証結果を今回の結果として扱わず、次に確認することと担当を残します。

関連する課題一覧やExcelは、決定記録のIDを参照します。記録だけを更新した場合は、課題一覧側の更新が済んだかどうかも明記します。新しい合意・実装・配備の証拠を得た時点で順次追記し、実施前の作業を完了扱いにしません。

この記録の作成・更新だけで、未確定の仕様を確定したり、実装・配備を承認したりしたことにはなりません。UI変更は引き続き[仕様確認・モック試用・実装](ui-prototype-workflow.md)の順で進めます。
