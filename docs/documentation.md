# ドキュメントの更新

このサイトは `docs/` のMarkdownを **MkDocs + Material for MkDocs** でビルドします。設定は `mkdocs.yml`、追加スタイルは `docs/stylesheets/extra.css` です。依存ライブラリは `requirements.txt` に含まれます。

## ローカルプレビュー

[開発環境](development.md)を用意し、リポジトリ直下で実行します。アプリとは別のポートを使います。

```bash
python -m mkdocs serve --dev-addr 127.0.0.1:8008
```

ブラウザーで `http://127.0.0.1:8008/` を開くと、Markdownの保存が反映されます。アプリの起動やDB接続は不要です。

## ビルドと検査

```bash
python -m mkdocs build --strict
git diff --check
```

生成先はGit管理外の `site/` です。別の作業結果を残したいときは `--site-dir tmp/mkdocs-review` を指定します。

追加スタイルは `hooks/docs_assets.py` が内容に応じたファイル名（`extra.<ハッシュ>.css`）で出力し、各ページから参照します。CSSの更新時にURLも変わるため、ブラウザーや配信先に残った以前のCSSによる表示崩れを防ぎます。編集するのは引き続き `docs/stylesheets/extra.css` です。公開時はHTMLとCSSを含む `site/` 全体を反映してください。

ナビゲーション漏れ、存在しないページ、未解決リンク、存在しない見出しアンカーを警告として検査し、strictビルドでは失敗にします。外部URLの到達性はこの検査の対象外です。現行設定の `exclude_docs` とリンク検査はMkDocs 1.6系を前提とし、今回の改訂は1.6.1で確認しています。

トップページ、長い表、コードブロックをブラウザーで確認し、狭い画面とダークモードでも読めることを確認します。

## どこを更新するか

トップの `index.md` は保育士や園で働く方に向けた、デモを最初に案内するやさしいページです。日常の場面を短い言葉で説明し、設定値・仕様表・技術的な変更履歴は `technical-guide.md` の「詳しい資料」から案内します。詳しい資料の既存ページは、その入口の下にまとめます。

| 変更内容 | 一緒に確認する文書 |
| --- | --- |
| 利用者向けの機能 | `features.md`、関連する使い方、`specifications.md` |
| URL・画面の導線 | `screen-transition-list.md` |
| 認証・権限・通知 | `accounts.md`、`notifications.md`、関連仕様 |
| 環境変数・起動条件 | `environment-profiles.md`、`security.md`、導入ガイド |
| DB・添付・worker | `architecture.md`、バックアップ仕様、運用手順 |
| 新しい公開ページ | `mkdocs.yml` のnav、入口となるページ |
| 日付付きの実装・配備記録 | `history.md`。確認日・対象版・未確認範囲も記載 |

## 現行仕様と過去の資料を分ける

「実装あり」「一部実装」「計画」「履歴」を区別します。過去の設計を残す場合は冒頭に現在との差と現行ガイドへのリンクを置き、古い「未実装」や当時のコマンドを現在の運用条件として読ませないようにします。

`exclude_docs` に列挙したローカルのレビュー・検討メモは公開ビルドと検索から外しています。公開するときは内容・リンクを確認してnavへ追加し、除外を解除します。navに載せないだけではファイルの公開除外になりません。

## 仕様の合意・変更・疑義を残す {#decision-records}

2026-11-01 JSTから、[仕様の決定・変更記録](spec-decisions.md)を共通の参照先とします。機能ごとの仕様書はそのまま維持し、決定記録と相互に参照できるようにします。

1. **対象を分ける**：対象機能・操作・権限・文書状態を明記し、要望、こちらの解釈、未確定事項を区別します。たとえば「管理者が編集できる」と「管理者名を担任欄へ自動入力する」は別の決定です。
2. **合意の根拠を残す**：合意日、確認できる会話・文書・モックの版を記録します。会話の識別子やリンクが取得できない場合はその旨と、日付・対象・必要最小限の発言を残し、参照を捏造しません。
3. **変更前の記録を残す**：新しい決定に旧IDと置換範囲を記載し、旧文書の冒頭にも新しい記録への参照を置きます。一部変更を文書全体の廃止と扱いません。最終合意に疑義があれば、旧決定を消さず「最終合意要確認」として追記します。
4. **合意・実装・配備・検証を分ける**：作業場所、ブランチ、コミット、未コミット差分の有無、配備先の版、確認日時・方法・結果を記録します。未コミット差分を含む場合は、可能なら差分や対象ファイルのハッシュを保存し、保存できていなければ再現性の限界を明記します。
5. **確認できていない点を引き継ぐ**：既存タスクの完了やコードの存在を、問題解決・最新の合意・本番反映の証拠に置き換えません。古い検証結果を今回の結果として扱わず、次に確認することと担当を残します。

関連する課題一覧やExcelは、決定記録のIDを参照します。記録だけを更新した場合は、課題一覧側の更新が済んだかどうかも明記します。新しい合意・実装・配備の証拠を得た時点で順次追記し、実施前の作業を完了扱いにしません。

この記録の作成・更新だけで、未確定の仕様を確定したり、実装・配備を承認したりしたことにはなりません。UI変更は引き続き[仕様確認・モック試用・実装](ui-prototype-workflow.md)の順で進めます。

## リンクと公開する情報

公開用のスクショ付きマニュアルは `docs/manual-guide.md` と `docs/manual-guide-preview/` に置きます。試作方針と公開範囲は[SD-012](spec-decisions.md#sd-012)を参照してください。撮影用の業務フォームは公開せず、マニュアルのUIと架空データの画像だけを配備します。画像・JS・CSSの版をそろえて表示・検索・画像拡大を確認します。 撮影元の表示だけで完了にせず、保存した画像そのものを開いて文字・全入力項目・番号枠の位置を確認し、公開後の画像拡大でも照合します。

同じサイトのページは `[表示名](page.md)` 形式にし、長い見出しへの参照には `{#maintenance}` のような明示アンカーを使います。`docs/` の外にあるコード・ツールはGitHubの対象ファイルへリンクし、生成物に対して `../tools/...` のような存在しない相対リンクを作りません。ローカルだけに保管している資料は、保管先をコード表記で記載します。GitHubへのリンクは、その版の対象ファイルが実際に公開されている場合に付けてください。

実データ、接続先、秘密値、個人名入りの操作履歴、未確認のPDFを公開資産へコピーしないでください。生成した `site/` は直接編集しません。

## 公開

このリポジトリのCIにはドキュメントのstrictビルドを含めます。公開サイト `open.hoikuict.net` はCloudflare Pagesの `open-hoikuict` プロジェクトから配信しています。`main` に公開対象をプッシュすると、Cloudflare Pagesがビルド・配備します（2026年9月23日確認）。ローカルの編集・ビルドだけでは公開サイトは更新されません。

公開時は対象ファイルを限定し、`python -m mkdocs build --strict` と差分を確認してからプッシュします。GitHubの対象コミットの **Cloudflare Pages** チェックが成功した後、公開URLを開き、本文・リンク・CSSの反映を確認します。CIの `test` とCloudflare Pagesの配備結果は別のチェックです。

2026-11-01の職員・保護者登録マニュアルの公開範囲と確認結果は[SD-009](spec-decisions.md#sd-009)に記録します。機能の実機配備、マニュアルのローカル作成、公開サイトへの掲載は別の状態として記録します。

[業務別マニュアル目次](manual-index.md)と手元の整備進捗表は[SD-010](spec-decisions.md#sd-010)を参照します。目次は公開し、進捗表は公開しません。進捗の更新時は既存Excelを読み、原稿・内容確認・公開の状態と確認日をそれぞれ更新してください。初期データからの再生成で、手元の更新を消さないようにします。

2026-11-23の新規5手順・日案の追記と40業務項目の進捗更新は[SD-066](spec-decisions.md#sd-066)を参照します。利用者の確認と公開依頼に基づき、公開URLまで照合済みです。更新したExcelは `outputs/01a2055b-7205-7453-8c24-fa6e37fb1b26/マニュアル整備進捗（2026-11-23公開反映）.xlsx` に保存しています。

2026-11-03の画面付き・状況別マニュアルのモックは[SD-012](spec-decisions.md#sd-012)を参照します。`tools/staff-manual-preview/` は試用中の案です。画面付き3例の作成を、全マニュアルの整備完了や公開仕様への合意として扱わないでください。正式な改訂では職員の試用結果と対象配備版を確認し、公開中の目次・手順・手元の進捗表の状態をそれぞれ更新します。

Windows導入アプリへのボタンは、公式GitHub Releasesの `releases/latest/download/OpenHoikuICT.exe` を参照します。配布版を更新するときは、公開するReleaseに同名の実行ファイルがあることと、[ダウンロードページ](download.md)の対応環境・版・サイズの説明を確認してください。

共通ヘッダーの「HPへ戻る」は、利用者の依頼に基づき2026-11-23に削除しました。再生成時も追加しません。[変更の根拠・範囲](spec-decisions.md#sd-067)。

文字サイズ切替は、ボタンの表記だけでなく本文・見出しの計算済みサイズと標準へ戻る動作まで確認します。[文字拡大の不具合と検査の補正](spec-decisions.md#sd-068)。

不足する画面付き手順は、確認版の制作 → 利用者の試読・修正 → 了承後のHP公開 → 次の制作の順で進めます。[SD-071](spec-decisions.md#sd-071)。第1回の出欠・緊急連絡先4本は2026-11-23の了承に基づき公開対象へ追加しました。進捗表の公開区分は、配信成功と公開URLの照合後に更新します。

第2回の職員ホーム・要確認一覧・児童票の5本は、利用者の「公開して」という依頼に基づき公開ガイドへ移しました。確認版の本文・画像を保持し、配信成功と公開先照合を確認してから手元の公開区分を更新します。[確認と公開の記録](spec-decisions.md#sd-071)。
