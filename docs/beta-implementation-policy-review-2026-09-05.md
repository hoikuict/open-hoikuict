# ベータ実装前の実装方針再考

確認日: 2026-09-05<br>
対象: main `c759415960d4eae04401cd28c2e3f967868279e4`、`kernel-lab/bootstrap`の仕様<br>

## 結論と評価の前提

単一アプリで業務機能を作り、SQLiteとローカル認証を使い、後から共通部分をカーネルへ抽出する骨格は、ベータ実装前として妥当である。ベータの前に汎用カーネル全体を完成させる必要はない。

ただし、現在の実装パターンをそのまま機能ごとに増やすと、競合検知、権限設定の検証、項目識別、トランザクション、データ移行の規則が分かれたまま定着する。この部分はベータ実装の共通ルールとして先に揃える。

実機運用・他園展開・長期利用がまだ確認されていないこと自体は、今回の欠点に数えない。前回作成した実証計画は後工程の候補であり、日案だけにベータの機能範囲を変更する決定ではない。本書は、現在予定しているベータを作りながら将来のカーネルへ進むための方針を評価する。

## 維持してよい方針

| 現行の選択 | 評価 |
| --- | --- |
| FastAPIの単一アプリ、サーバーで画面を生成する構成 | 業務単位で実装・試験しやすい。カーネル化のために別サービス群や別のフロントエンドへ作り直す理由は、今回の確認では見つからない。 |
| SQLite・SQLModel | 現段階の採用は妥当。将来の規模や実測結果に応じて再評価する。今の課題はDB製品の選択より、更新単位と移行方法の明確化にある。 |
| ローカル認証と明示的な保護者・園児関係 | 現行実装を引き継ぐ。カーネル化で認証を再実装することを目的にしない。 |
| 業務ごとのモデルと履歴 | 観察、計画、請求などの意味を保てる。全データを一つの汎用Recordテーブルにまとめる必要はない。 |
| 設定の版を保存し、記録から参照する | [設定版と記録の関係](C:/python/open-hoikuict/child_records/models.py:14)は伸ばすべき土台。設定変更で過去の記録の解釈を変えない方針を維持する。 |
| 内部IDと公開IDの併用 | [観察記録のpublic_id](C:/python/open-hoikuict/child_records/models.py:38)のような追加方式を使える。既存主キーの一斉UUID化は必要ない。 |

施設文例の別DBや添付ストレージも、カーネル仕様の図に合わせるためだけに統合しない。複数の保存先があることを現状として認め、どの業務の正本か、どこまで一括更新できるかを定義する。

## 今修正すべき実装ルール

### 1. 重要な記録更新は、履歴保存と競合検知を両方備える

日案には[expected_lock_versionによる競合検知](C:/python/open-hoikuict/plan_docs/store.py:306)があり、園内記録にも[版番号を条件にした更新](C:/python/open-hoikuict/institutional_record_service.py:384)がある。一方、[観察記録の訂正](C:/python/open-hoikuict/child_records/router.py:640)は、訂正前の履歴を残すが、画面を開いた時点の版を検査しない。

隔離したメモリ上のSQLiteで、同じ内容の訂正画面を二つ開いた後、Aが本文を変更し、Bが古い本文のまま振り返りだけ変更する操作を再現した。両方の保存が303で成功し、Aの変更は現在の本文から消えた。Aの変更は履歴には残るため、履歴そのものの消失とは区別する。

**決める規則:** 複数の利用者・画面から編集される重要な記録には、読込時の版を保存要求へ含め、DB更新条件でも一致を検査する。不一致は競合として返し、利用者の未保存入力を保持する。履歴番号を採番するだけでは、この代わりにならない。

これは汎用カーネルの完成を待たず、まず既存の日案・園内記録の方式を参考に観察記録へ適用できる。

### 2. 権限設定の「未設定」と「不正な値」を分ける

[設定保存](C:/python/open-hoikuict/child_records/router.py:196)と[設定解釈](C:/python/open-hoikuict/child_records/access.py:19)は、知らない閲覧範囲を`all_staff`へ補正する。架空の設定要求で`assigned_clas`という誤った値を送ったところ、303で成功し、`all_staff`が保存された。

**決める規則:** 既定を全職員閲覧にする現在の業務方針は維持する。旧設定に項目が存在しない場合の互換処理は明示する。一方、新しい設定要求の不正値は422等で拒否し、現在の有効な設定を変更しない。保存済み設定の未知のschema版・不正値も、黙って広い権限へ解釈しない。

将来AIや外部ツールが設定を生成しても、この同じ検証を通す。画面で選択肢を制限するだけでは共通の契約にならない。

### 3. 拡張項目の識別子を、表示名から独立させる

現在の[custom_field_key](C:/python/open-hoikuict/child_records/settings.py:206)は表示名を材料にUUIDを生成し、[設定保存](C:/python/open-hoikuict/child_records/router.py:219)は項目名一覧から定義を作り直す。このため、項目の名称変更は別のkeyになる。

過去の観察記録には設定版への参照があるため、名称変更だけで過去の値が消えるとは評価しない。ただし、「同じ項目の名前を変えた」と「別項目を追加した」を明示的に区別できず、年度をまたぐ集計や後の拡張APIで意味が途切れる。

**決める規則:** 項目作成時にIDを発行し、その後はlabelと別に保持する。名称変更、非表示・廃止、意味や型の変更を区別する。既存keyは引き続き解決可能にし、新旧対応を残す。設定JSON全体のschema版と、園が保存する設定内容の版も区別する。

同じ考え方を園・クラスの公開参照へ適用する。内部整数IDはそのまま使い、氏名・園名・クラス名を新しい永続識別子として増やさない。

### 4. 「一つの操作をどこで確定するか」を揃える

現在は[保育計画Repositoryがcommitする](C:/python/open-hoikuict/plan_docs/store.py:217)方式、[園内記録サービスはflushまで行う](C:/python/open-hoikuict/institutional_record_service.py:308)方式、観察記録のRouterが直接更新・commitする方式が併存する。

個別の操作で正しく動いていることと、複数の操作を安全に組み合わせられることは別である。途中でcommitする処理を複数つなぐだけでは、後段の失敗時に全体を取り消せない。今回、現行の日案の承認・通知処理が分断されていると確認したわけではなく、同処理は関連更新を一つのcommitにまとめている。

**決める規則:** 新設・変更する更新経路は、操作主体、対象、必要な権限、入力検証、版検査、更新、監査を扱う業務サービスを入口にする。一つの業務操作を統括する処理がcommitを所有し、下位の書込み処理は単独で確定しない。外部配送は確定後に処理する。

既存のcommitを機械的に除去しない。外側の業務処理へ確定責務を移し、失敗時に本文・履歴・通知依頼がどう残るかを試験する。CLIや将来のAI連携も、HTTPの画面処理を直接呼び出すのでなく、この業務サービスを通す。

### 5. 起動処理と、版を進めるデータ移行を分ける

[通常起動](C:/python/open-hoikuict/main.py:85)から[スキーマ作成・多数のmigration](C:/python/open-hoikuict/database.py:49)と[家族・健康情報の補正](C:/python/open-hoikuict/database.py:1183)が実行される。migration失敗を例外で止める点は良い。一方、現状は適用済みの版を管理する台帳による実行制御ではなく、列の有無やデータの状態を毎回調べる構成である。

**決める規則:** 継続保持するベータデータを扱う前に、スキーマ版・移行ID・適用履歴を管理する。初期作成、過去データの補正、通常起動時の版確認を区別する。業務データを書き換える移行は対象版と実行契機を明示し、再実行・途中失敗からの復旧を試験する。

旧`extra_data`、健康情報、家庭共有情報などは、項目ごとにどれが正本か、互換データをどちら向きに同期するかも定義する。新しいサービスへ移した後に、起動時の古い補正処理が別経路から上書きする構成を増やさない。

特定のmigration製品の導入や、過去の全migrationの一括書き直しを、この提案の必須条件にはしない。まず現在のSQLiteを基準に、更新履歴と実行境界を持たせる。

## ベータで変えてよいものと、今から守るもの

| ベータで調整する | 変更時にも維持する契約 |
| --- | --- |
| 入力画面、表示名、必須項目、帳票、記録頻度 | 項目のID、保存時の設定版、既存記録の解釈 |
| 業務上の閲覧範囲、承認手順 | 誰の権限で行ったか、検証済みの設定、過去の承認版 |
| モジュールの配置、内部クラス・関数の構成 | 公開参照の互換性、更新の確定単位、履歴と競合の扱い |
| 将来のAI接続先・モデル・利用画面 | データの送信可能範囲、入力検証、認可、変更の追跡 |

カーネルの共通部分に固定するのは「承認が必要な業務はどれか」のような園ごとの選択そのものではなく、「承認した版を勝手に別内容へ変えない」といった仕組みである。業務の意味が異なる履歴を、一つの表や一つの状態遷移へ無理に統合しない。

## ベータ前の必須作業にしないもの

- 複数施設を一つのDBで運用する機能全体。今は単一施設という前提と安定した参照を明示し、テナント分離を保証済みとはしない。
- 汎用プラグインSDK、配布パッケージ、マニフェスト署名、全機能の宣言型UI。
- 稼働プロセスを分割するためのサービス群、全テーブルの共通モデル化、DB製品の変更。
- 外部AIを接続しないベータでのAI Gateway一式。ただし外部AIを有効化する前には、送信範囲と強制経路を実装する。既存の日案仕様の例外とカーネル方針の優先関係は先に解決する。

これらを先送りしても、将来の入口となる業務サービス・識別子・版・権限・移行履歴は今から揃えられる。拡張機構の完成と、拡張しても壊れない契約の整備を同じ工程にしない。

## 推奨する実装順

1. 観察記録の古い画面からの上書きと、権限設定の不正値受入を修正する。上記の再現条件を回帰試験として残す。
2. 新しい設定・更新機能について、安定した項目ID、設定検証、競合検知、トランザクション所有者を実装ルールにする。既存機能は変更する経路から揃える。
3. 記録を継続保持するベータに向け、スキーマ版と明示的なデータ移行を導入する。ID・時刻・正本データの移行規則を添える。
4. 現在予定しているベータ機能を、このルールで実装・検証する。全機能を先にカーネルへ移す工程は置かない。
5. 業務で繰り返し必要になった共通処理をカーネルとして抽出する。ベータで変わる業務ルールは、設定または業務モジュール側に残す。
