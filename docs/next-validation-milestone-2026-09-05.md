# 次の実証計画：日案の一巡と運用の引き継ぎ

## この計画で確かめること

open-hoikuictには、ローカル認証、職員権限、保育計画の版管理・承認、通知、バックアップなど、運用の土台になる実装がある。一方、実機での継続利用、障害からの復旧、開発者以外への引き継ぎは、今回確認した証拠では評価できない。汎用カーネルは仕様段階で、複数の園の違いを吸収できることも未実証である。

次の到達点を「架空データで日案業務が一巡し、再起動・復元後にも記録の意味が保たれ、開発者以外の人も操作できる」とする。第一候補に日案を選ぶ理由は、既に保存・版競合・承認版保護・振り返りの実装とテストがあり、現場での使い勝手とカーネルへ引き継ぐ契約を同時に確認できるためである。

本書は[サーバー運用試験仕様書改訂版](C:/python/open-hoikuict/docs/pilot-deployment-spec-v2.md)の段階A・Bにおける重点業務を具体化する。認証・保護者分離・バックアップ等の既存受入条件を置き換えたり、段階Cの実データ試験を許可したりする文書ではない。

## 最初に固定する範囲

- 架空の1園・1クラス相当の日案を使う。実在する園児・家庭・職員の業務データは投入しない。
- 職員2〜5名の範囲で、作成者・承認者・閲覧専用者を識別する。可能なら、開発者以外の人を操作確認者に含める。
- 作成、修正、提出、承認、実施変更・振り返り、過去版参照を一つの流れとして扱う。
- 展開するSHA・image・構成を記録する。途中で修正した場合は版を分け、影響する試験を再実施する。
- 実データ試験に進む条件、復旧目標、公開制御は既存の運用試験仕様に従う。

## 成果の測り方

| 観点 | 記録する値・事実 | 判断への使い方 |
| --- | --- | --- |
| 業務への効果 | 同じ架空の業務を従来手順とアプリで行った所要時間、転記回数、訂正回数 | 時短だけでなく、見落としや引き継ぎの改善も確認する。数値目標は初回の比較後に決める |
| 操作の分かりやすさ | 開発者の説明なしで完了した操作、つまずいた箇所 | 機能追加より先に改善すべき導線を決める |
| 記録の信頼性 | 保存欠損、無言の上書き、承認版の変化、権限外操作の成否 | 一つでも確認されたら影響範囲を調べ、解消と再試験を優先する |
| 運用負担 | バックアップ・更新・問い合わせ対応の作業時間、開発者にしかできない作業 | 園側が継続して扱える範囲と支援が必要な範囲を明確にする |
| 復旧 | 復旧した時点、欠けた記録、復旧にかかった時間 | [既存の復旧目標](C:/python/open-hoikuict/docs/pilot-deployment-spec-v2.md:234)と比較する |

一巡の実証完了にはV01〜V08の実測と問題の整理が必要。機能が動かない項目は失敗または条件付きと記録する。段階B・Cへの移行判断では、運用試験仕様の全条件を別途確認する。本人以外の確認者がいない場合、引き継ぎ可能性は未確認のまま残す。

## 実証後のカーネル開発

1. 実証中に変えてはいけないと確認できた契約を固定する。最初の候補は操作主体、権限、文書ID、版・承認状態、時刻、監査である。
2. [整合性確認書](C:/python/open-hoikuict/docs/kernel-main-consistency-review-2026-09-05.md)の移行条件を、カーネル仕様の別改訂版に反映する。
3. 現行mainを基準に一つの業務経路から共通処理を抽出し、移行前後で同じ実証シナリオとテストを通す。
4. 別のクラスや園で実際に異なる項目・帳票・承認手順を一件選び、共通部分を改変せずに設定または拡張で対応できるか試す。まだ得られていない要求を実在の要求として扱わない。
5. 変更前の記録を引き継げること、変更を比較・確認できること、戻せることを確かめてから、AIによる変更提案や設定生成を接続する。

全機能の汎用化や、すべてのAI基盤の構築を、この実証の前提にはしない。実証中の改善は、記録の欠損・権限・操作上の支障・復旧不能など、試験で判明した問題に優先順位を付ける。
